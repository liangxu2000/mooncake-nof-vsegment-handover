# 条带与分块三层参数说明

- 日期：2026-11-26
- 适用拓扑：reader node2；master+etcd node4；两个远端 target：node3（A）+ node4（B）
- 当前配置：`member_count=2`、`stripe_size=2MiB`、`member_extent_size=50GiB`、NoF `chunk=128KiB`、target RAID0 `strip=256KiB`、每 target 11 块盘

---

## 0. 一句话

一个 4MiB key 要经过**三层切分**才落到盘上：

```text
4MiB key
  │
  ├─ 第 1 层：vsegment stripe_size = 2MiB
  │     → 2 个 2MiB child，分别落到 node3 / node4 两个 target
  │
  ├─ 第 2 层：NoF submit chunk = 128KiB
  │     → 每个 2MiB child 切成 16 个 128KiB 子 IO
  │
  └─ 第 3 层：target RAID0 strip = 256KiB
        → 每个 128KiB 子 IO 按起始地址落到某一块盘
```

三层各自负责不同的事，**不能混着理解**：

| 层 | 参数 | 当前值 | 谁决定 | 负责什么 |
|---|---|---|---|---|
| vsegment 逻辑条带 | `stripe_size` | **2MiB** | master 的 vsegment profile | 一个 key 拆成几个 child、每个 child 去哪个 member/target |
| NoF 提交切片 | `MC_NOF_SUBMIT_CHUNK_BYTES` | **128KiB** | 客户端常量/env | 一个 child 切成几个 NoF 子 IO |
| target RAID0 条带 | `strip_size` | **256KiB** | target 的 RAID0 bdev 配置 | 一个 128KiB 子 IO 落到哪块盘、盘内偏移是多少 |

---

## 1. 第 1 层：vsegment 逻辑条带（stripe_size = 2MiB）

### 1.1 它是什么

vsegment 把 key 的**逻辑地址空间**按 `stripe_size` 切成条带，条带轮流分配给 `member`（member 数量 = `member_count`）：

```text
member_count = 2
stripe_size  = 2MiB

4MiB key 的逻辑地址：
  0          2MiB         4MiB
  |--stripe0--|--stripe1--|
       │            │
       ▼            ▼
   member0      member1
   node3 A      node4 B
```

- `stripe0 [0, 2MiB)` → member0（node3）
- `stripe1 [2MiB, 4MiB)` → member1（node4）

所以一个 4MiB key 在 Mooncake 传输层是 **2 个 child**，每个 2MiB，一个 target 一个。

### 1.2 映射公式

源码 `ResolveTransfer`（`vsegment_runtime.cpp:339`）对每个逻辑位置做：

```text
stripe_index    = floor(logical_offset / stripe_size)
member_index    = stripe_index % member_count
member_round    = floor(stripe_index / member_count)
physical_offset = member.base_offset
                + member_round × stripe_size
                + (logical_offset % stripe_size)
```

对 `member_count=2`、`stripe_size=2MiB`：

| stripe_index | member_index | 落到谁 |
|---|---|---|
| 0 | 0 | node3 A |
| 1 | 1 | node4 B |
| 2 | 0 | node3 A |
| 3 | 1 | node4 B |
| … | … | 交替 |

### 1.3 是条带，不是副本

- `member_count=2` 表示 key 的数据**分成两半**放在两个 member 上；
- 每个 target 只存这个 key 的一半（2MiB），**不是各存一份 4MiB**；
- 总物理占用仍然是 4MiB（2MiB + 2MiB），没有翻倍；
- 如果要副本，那是 `replica_num` 的概念，不是 `member_count`。

### 1.4 为什么当前选 2MiB

| stripe_size | 4MiB key 的结果 | 评价 |
|---|---|---|
| **2MiB（当前）** | 2 个 child，node3/node4 各一个 2MiB | 两个 target 都用上，child 数最少 |
| 4MiB | 1 个 child，4MiB 全落一个 member | 另一个 target 空闲，等于没用上双 target |
| 1MiB | 4 个 child，两个 member 各两个 1MiB | 更细的并行，但 task/child 数翻倍 |
| 512KiB | 8 个 child | 更碎，通常不值得 |

`stripe_size` 只是**逻辑切分粒度**，不是盘上的物理条带；盘上的物理条带是第 3 层的 256KiB。

---

## 2. 第 2 层：NoF 提交切片（chunk = 128KiB）

### 2.1 它是什么

Mooncake 的 NoF 路径不会把一个 2MiB child 当成一个 2MiB 请求直接发；它按 `MC_NOF_SUBMIT_CHUNK_BYTES`（默认 128KiB）把 task 切成子 IO：

```text
2MiB child
  → 16 × 128KiB NoF 子 IO
  → 16 个请求分别提交到 target
```

一个 4MiB key：

- plain：1 个 4MiB task → **32 × 128KiB**
- vseg：2 个 2MiB child → 每个 16 × 128KiB → 合计 **32 × 128KiB**

所以两臂在 target 看到的**子 IO 总数和大小相同**，区别只是它们分布在几个 target、属于几个 task。

### 2.2 源码位置

| 内容 | 位置 |
|---|---|
| 默认 chunk 常量 `kDefaultSpdkNofSubmitChunkBytes = 1<<17`（128KiB） | `transfer_task.h:625` |
| env `MC_NOF_SUBMIT_CHUNK_BYTES` 读取 | `transfer_task.cpp:145` |
| `blocks_per_chunk = chunk_bytes / block_size` | `transfer_task.cpp:655` |
| 按 chunk 切子 IO 的提交循环 | `transfer_task.cpp:1202` 附近 |

block_size = 512B 时，128KiB = 256 blocks；2MiB = 4096 blocks。

### 2.3 可调，但有上限

- 这个值可以用 env 改；
- 但 NOF-113R 实测：chunk 调到 ≥256KiB 后，target 实际单 IO 仍被夹在 **256KiB**（target n 从 16898 掉到 8450），所以继续加大 chunk 不会让 IO 更大；
- 它和第 3 层的 256KiB strip 是两回事：一个是客户端提交粒度，一个是 target 盘地址窗口。

---

## 3. 第 3 层：target RAID0 条带（strip = 256KiB）

### 3.1 它是什么

target 把 11 块盘做成一个 RAID0 bdev。RAID0 把**逻辑地址空间**按 `strip_size` 切成固定窗口，轮流分配给 11 块盘：

```text
target 逻辑地址（每个窗口 256KiB，轮流分给 11 块盘）：

0        256K      512K      768K     1024K
|--disk0--|--disk1--|--disk2--|--disk3--| ...
 ^ 128K IO   ^ 128K IO
   → disk0      → disk0
```

关键点：

- **strip 是“地址窗口”，不是“IO 大小”**；
- 一个 128KiB IO 落在哪个窗口，由它的**起始地址**决定；
- 128KiB < 256KiB，且我们的 IO 都是 128KiB 对齐，所以一个 IO 只占窗口的一半，**不会跨窗口**，只落一块盘；
- 如果 IO 未对齐、跨了 256KiB 边界，RAID0 才会把它拆成两块盘的两个 IO。

### 3.2 映射公式

按字节：

```text
strip_index     = floor(byte_offset / 256KiB)
disk            = strip_index % 11
offset_on_disk  = floor(strip_index / 11) × 256KiB + (byte_offset % 256KiB)
```

按 LBA（512B 块）：

```text
disk = floor(lba / 512) % 11
```

### 3.3 具体例子：4MiB key、128KiB 子 IO

一个 4MiB key 起始 LBA = `i × 8192`（因为 4MiB / 512B = 8192 blocks）。

plain 的 32 个 128KiB 子 IO，第 k 个（k=0..31）起始 LBA：

```text
lba(k) = i × 8192 + k × 256
```

它落到的盘：

```text
disk(k) = floor((i × 16 + k / 2)) % 11
```

由于 `k/2` 取整，**连续两个 128KiB 子 IO 落同一块盘**：

| k | 子 IO 地址范围（块） | 256KiB 窗口 | 盘 |
|---|---|---|---|
| 0 | 0–255 | 窗口 0 | disk0 |
| 1 | 256–511 | 窗口 0 | disk0 |
| 2 | 512–767 | 窗口 1 | disk1 |
| 3 | 768–1023 | 窗口 1 | disk1 |
| 4 | 1024–1279 | 窗口 2 | disk2 |
| … | … | … | … |

所以：

- 一个 2MiB child = 16 个 128KiB 子 IO = 8 个 256KiB 窗口 = **8 块盘**；
- 一个 4MiB plain key = 32 个 128KiB 子 IO = 16 个窗口，11 块盘轮流，**有的盘拿到两个窗口**；
- 两个 target 各自有自己的 11 盘 RAID0，分别独立做这个映射。

### 3.4 strip 大小的影响

| strip | 每块盘一次拿到 | 对 128KiB 子 IO 的影响 |
|---|---|---|
| 128KiB | 1 个 128KiB 窗口 | 每个子 IO 换一块盘 |
| **256KiB（当前）** | 2 个 128KiB 窗口 | 连续两个子 IO 同一块盘 |
| 512KiB | 4 个 128KiB 窗口 | 连续四个子 IO 同一块盘 |

strip 不改变 vseg 的 child 切分，也不改变 NoF 的 128KiB 提交粒度；它只改变这些 128KiB 子 IO 在盘上的分布。

## 4. 三层合起来：一个 4MiB key 的完整路径

```text
4MiB key（逻辑）
│
├─ vsegment stripe_size = 2MiB
│   ├─ stripe0 2MiB → member0 / node3 target A
│   │     └─ NoF chunk 128KiB → 16 个子 IO
│   │           └─ RAID0 strip 256KiB → 每个子 IO 落 node3 的某块盘
│   │
│   └─ stripe1 2MiB → member1 / node4 target B
│         └─ NoF chunk 128KiB → 16 个子 IO
│               └─ RAID0 strip 256KiB → 每个子 IO 落 node4 的某块盘
│
└─ 合计：两个 target 各 16 个 128KiB 子 IO，并行完成
```

对比 plain：

```text
4MiB key（逻辑）
└─ 1 个 4MiB task
      └─ NoF chunk 128KiB → 32 个子 IO
            └─ RAID0 strip 256KiB → 全部落 node4 的 11 块盘
```

两臂 target 侧的总 IO 数、单 IO 大小相同（32 × 128KiB），区别是：

- plain：32 个子 IO 全在 node4 一个 target；
- vseg：16 个在 node3、16 个在 node4，两个 target 并行。

## 5. 常见误解

### 误解 1：strip=256KiB，子 IO 只有 128KiB，是不是只用了半个 strip？

不是。strip 是地址窗口；128KiB 子 IO 只占 256KiB 窗口的一半，但它仍然完全属于这个窗口，所以只落一块盘。窗口的另一半由下一个 128KiB 子 IO 使用。

### 误解 2：stripe_size 和 strip 是同一个东西

不是：

- `stripe_size` 是 vsegment 的**逻辑**切分，决定 child 和 member；
- `strip` 是 target RAID0 的**物理地址**切分，决定盘号；
- 两者之间还隔着 NoF 的 128KiB 提交切片。

### 误解 3：member_count=2 是两个副本

不是。`member_count=2` 是**条带**：每个 target 存一半。副本是 `replica_num`，两者语义不同。

### 误解 4：chunk 调大，IO 就会按 2MiB 落到盘上

不一定。NOF-113R 实测 target 实际单 IO 被夹在 256KiB；而且即使 chunk 变大，RAID0 仍然按 256KiB 窗口映射盘号。

### 误解 5：vseg 的 2 个 child 就是 target 看到的 2 个 IO

不是。child 是 Mooncake 传输层概念；每个 2MiB child 在 NoF 层会被切成 16 个 128KiB 子 IO。target 看到的是 32 个子 IO（两个 target 各 16 个）。
