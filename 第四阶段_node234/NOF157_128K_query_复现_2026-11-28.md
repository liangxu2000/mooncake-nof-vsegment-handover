# NOF-157 128K query 差复现（60,000 keys × E0/E1）

- 日期：2026-11-28
- 性质：**诊断**（60k keys、plain NoF + null bdev、diag-on），不写正式表
- 目的：按用户要求把 NOF-155/156 的 400-key 复核升级到 **60,000 keys**，回答四件事：
  1. 128K 的 E0 query 低值（69/76）在 60k 下是否复现；
  2. E1 的 94/82 式漂移是否复现，E0/E1 query 是否有稳定臂间差；
  3. 4M 前后锚点的 query 漂移能否解释 128K 的臂间差；
  4. target 侧 128K·E1 单 IO 更快（17.7→26.9µs 的“回升”）是否复现。

---

## 结论摘要

- **128K E0 query 在 60k 下不复现低值**：3 遍 **88.0 / 85.0 / 84.0µs（中位 85.0）**，全部 ≥84；NOF-155/156 的 72.5（69/76）是 **400-key 规模/当时窗口的产物**，不是 E0 臂固有属性。
- **E1 也不再漂移**：3 遍 **86.0 / 82.0 / 83.0µs（中位 83.0）**，遍内极差仅 4µs（NOF-156 为 12µs）；E0−E1 query 差 **+2.0µs**，方向上与 400-key 相反、量级可忽略 ⇒ **query 无稳定臂间差**。
- **4M 前后锚点极稳**：query 漂移 E0 **+1.0µs**、E1 **+0.0µs**；P50 漂移 +4.4/+5.1µs ⇒ 不能也不需要解释 128K 臂间差。
- **target 侧 128K·E1 更快稳定复现**：E0 **38.9µs/IO** vs E1 **29.4µs/IO**，Δ **+9.5µs**；3 遍各自很紧（37.7–39.3 / 25.7–29.6）。4M 侧 E0 89.1/89.0 vs E1 33.8/33.8，与 NOF-153 的 88.6/33.4 一致。
- **128K 的 P50 臂间差 +42.5µs 几乎全部来自数据面**：query 只差 +2.0µs；`read` 差 **+40.0µs**；target push JFC 差（E0 32.4 vs E1 23.0，中位）与 NOF-152/153 结论一致。
- **判决**：NOF-155 的「128K E1 优势掉到 17.4µs」是 **400-key query 污染**；60k 下 128K E1 仍快 **42.5µs（P50）**，没有崩塌。**拆细仍然不改善端到端**（128K 比 4M 慢：E0 277.2 vs ~237.9、E1 234.7 vs ~177.9）。

## 五、判读（四问）

### 5.1 128K E0 query 是否 3 遍都 <80

**否。** 88.0 / 85.0 / 84.0，中位 85.0，全部 ≥84。NOF-155/156 的 72.5（69/76）**在 60k 下不复现** ⇒ 该低值是 400-key 规模/当时窗口的产物，不是 E0 臂固有属性。

### 5.2 E1 是否仍 94/82 漂移，query 是否有稳定臂间差

**都不高，也不再漂移。** E1 86.0 / 82.0 / 83.0，中位 83.0，遍内极差 4µs（NOF-156 为 12µs）。E0−E1 = **+2.0µs**，方向与 400-key 相反、量级可忽略 ⇒ **query 无稳定臂间差**。query 是 Master RPC，EID 只作用于 NoF 数据面，本结果与机制一致。

### 5.3 4M 前后锚点能否解释 128K 臂间差

**不能也不需要。** 锚点 query 漂移 +1.0/+0.0µs、P50 +4.4/+5.1µs，窗口极稳；且 128K 的 query 本身无臂间差。

### 5.4 target 128K E1 是否仍更快

**是，稳定复现。** E0 38.9 vs E1 29.4µs/IO（Δ+9.5），3 遍各自紧（37.7–39.3 / 25.7–29.6）；与 NOF-155 的 37.5/26.9 同向同量级。4M 侧 E0 89.1/89.0 vs E1 33.8/33.8，与 NOF-153 的 88.6/33.4 一致。

### 5.5 P50 臂间差 +42.5µs 的来源

- query 只差 +2.0µs，**几乎全部来自数据面**：`read` 差 +40.0µs（181 vs 141）。
- target 单 IO 差 +9.5µs；128K 每 key 32 个 IO，在 4-qpair 上流水后压缩为 read 的 +40µs。
- push JFC 中位 E0 32.4 vs E1 23.0（Δ+9.4），与 NOF-152/153 的“差额在 target push JFC”一致；W9 两侧均 5.9µs，不是 W9。

## 八、裁定与下一步

### 已可定案

1. **NOF-155/156 的「128K E0 query 低」是 400-key 规模/窗口现象**；60k 下 E0 85 / E1 83，query 无稳定臂间差（Δ+2.0µs）。
2. **NOF-155 的「128K E1 优势掉到 17.4µs」作废**：60k 下 128K E1 仍快 **42.5µs（P50）**，其中 query 仅 2.0µs，read 差 40.0µs；target t/IO 差 9.5µs（push JFC）。
3. **128K E1 的 target 侧优势稳定复现**（38.9 vs 29.4µs/IO），4M 侧也复现（89.1/33.8）。
4. **拆细仍不改善端到端**：128K 比 4M 慢（E0 277.2 vs ~237.9；E1 234.7 vs ~177.9）。

### 下一步

- NOF-155 报告已按本单更新：128K 的 17.4 不再作为“E1 优势崩塌”的证据，改为“400-key query 污染；60k Δ42.5”。
- **NOF-158（未下发）**：真实 vsegment 路径验证“放大 chunk”——`MC_NOF_SUBMIT_CHUNK_BYTES=2MiB`（每个 2MiB child 1 IO）vs 128KiB，E1/E0，先 400-key 探针；vsegment child 是否认该 env 未测（旧 NOF-015 认为固定 128KiB）。
- target JFC 旋钮（`num_jetty_per_ep`/`jfc_depth`）仍需重启 target，暂不动；在 128K 下 E1 已有 42.5µs 端到端优势，是否值得为 E0 调 target 另议。
