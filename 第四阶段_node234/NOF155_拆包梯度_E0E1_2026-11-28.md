# NOF-155 拆包梯度：4MiB → 128KiB × E0/E1（plain NoF + null bdev）

- 日期：2026-11-28
- 性质：**诊断**（400 keys、null bdev、diag-on），不写正式表
- 目的：固定 4MiB key，把同一个包按客户端 submit chunk 拆成 4MiB/2MiB/1MiB/512KiB/256KiB/128KiB，看 **target 单 IO 成本**、**每 key target 串行累加**、**端到端每 key 时延** 三者随拆细如何变化，验证“target 侧降、但更多 IO 的网络+框架开销把端到端收益吃掉”的假设。

---

## 结论摘要

- **26/26 遍全部跑通，failed=0**；拆包自证 100% 吻合：`sub_ios=N`、`blocks=chunk/512`、`read_ops=528·N`。
- **target 单 IO 确实随拆细下降**：E0 **88.6→37.5µs（−58%）**，E1 **33.4→26.9µs（−19%）**；E0−E1 的单 IO 差 **55.2→10.6µs（−81%）**，逐档仍几乎全部落在 push JFC wait。
- **但每 key 的 target 串行累加（N×单IO）暴涨**：E0 **88.6→1200.8µs（13.6×）**，E1 **33.4→861.5µs（25.8×）**。
- **端到端没有净收益，反而变慢**：P50 E0 **231.7→258.5µs（+27µs/+11.6%）**，E1 **181.2→241.1µs（+60µs/+33.1%）**；256K 处 E0 达到 289.1µs 峰值。
- **E1 相对 E0 的端到端优势**：4M–256K 稳定在 **+46.8～+57.2µs**，128K 收窄到 **+17.4µs**（但 128K 的 query E0/E1 差 15.5µs，同 query 归一后约 **33µs**；见 5.4.1）。
- **判决（本实验：null bdev、400 keys）**：拆细只降低 target 单 IO 成本，不降低每 key 端到端；正式口径的 128KiB chunk（32 IO/key）落在“多 IO、端到端偏差”的一端（128K E0 258.5 > 4M 231.7；256K E0 289.1 更高）。**继续往更小拆没有价值；值得反过来验证“把 chunk 放大”**（见第八节）。

## 二、结构图（先看图）

### 2.1 两端：4MiB 不拆（N=1）

```
4MiB key, chunk=4MiB
E0: query 90 ─ read 131 ─ total 232µs
                  └ target 88.6 (push JFC 87.0)
E1: query 91 ─ read 83 ─ total 181µs
                  └ target 33.4 (push JFC 31.7)
```

- N=1 时 `read_us − target_us` ≈ 42/50µs，可近似看作 **target 之外的网络+客户端框架开销**。E1 省的 55µs 几乎完整落到端到端（P50 差 50.5µs）。

### 2.2 另一端：128KiB 拆 32 份（N=32）

```
4MiB key, chunk=128KiB
E0: query 72.5 ─ read 177 ─ total 258.5µs
                  └ target 单IO 37.5 × 32 = 1200.8（串行上界）
                     实际 read 177 ⇒ 大量 IO 重叠
E1: query 88 ─ read 140.5 ─ total 241.1µs
                  └ target 单IO 26.9 × 32 = 861.5（串行上界）
                     实际 read 140.5 ⇒ 大量 IO 重叠
```

### 2.3 趋势一眼看

```
target 单IO:  E0 88.6 → 37.5 (↓58%)    E1 33.4 → 26.9 (↓19%)
E0−E1 单IO:   55.2 → 10.6 (↓81%)       逐档 ≈ push JFC 差
每key target: E0 88.6 → 1200.8 (↑13.6×) E1 33.4 → 861.5 (↑25.8×)  ← 串行上界
端到端 P50:   E0 231.7 → 258.5 (↑27)    E1 181.2 → 241.1 (↑60)     ← 实际墙钟
```

**单 IO 在降、每 key 在涨、端到端不降**——这就是本单的核心。

## 五、判读

### 5.1 拆得越细，target 降多少、端到端降多少

- **target 单 IO**：E0 88.6→37.5µs（−58%），E1 33.4→26.9µs（−19%）。E0 降得更多，因为它的 push JFC 固定等待从 87µs 降到 31.6µs；E1 的 push 本来只有 31.7µs，降到 21.4µs。
- **E0−E1 单 IO 差**：55.2→10.6µs，逐档与 push JFC 差重合（55.2/55.4、41.2/41.3、34.8/34.7、29.5/29.6、22.7/22.5、10.6/10.2）⇒ **E0/E1 的单包差仍然几乎全部是 push C2H 等待**。
- **每 key target 串行累加**：E0 88.6→1200.8µs（13.6×），E1 33.4→861.5µs（25.8×）。IO 数 1→32，把固定成本放大了。
- **端到端 P50**：E0 231.7→258.5µs（+27），E1 181.2→241.1µs（+60）。**没有一档比 4M 更快**；256K 的 E0 289.1µs 是峰值。

### 5.2 差额去哪了：不是“被网络吃掉”这么简单

- `res = read − N×t/IO` 从 4M 的 +42/+50 变到 128K 的 **−1024/−721**。负值说明 **N 个 IO 在 4 个 qpair 上并发流水**，target 串行累加根本没落到墙钟。
- 但 `read_us` 仍随 N 增长（E0 131→177，E1 83→140.5），`completion_wait` 增长更明显（E0 118→169，E1 70→129.5）。**每 key 墙钟的两个大项是 query（~90µs，基本不变）和 `read_us` 内的 wait（随 IO 数增长）**；不能把 query 与 wait 直接相加当总时延。
- 因此准确表述是：**target 单 IO 的收益被“更多 IO 的提交/完成/排队开销”抵消，且抵消量大于收益**；不是“收益被弱化”，而是“端到端没有净收益、E1 反而变慢”。
- 由于没有 per-IO 的客户端时间戳，**无法把增长精确拆成“网络在飞”与“框架开销”**；`read_us−target_us` 在 N>1 时不能当纯网络。

### 5.3 `read_us − target_us` 的正确口径

- **N=1（4M）**：`read_us` 是每 key 数据面，`target_us` 是 target 每 IO；相减 ≈ target 之外的网络+客户端框架。4M 为 42.4/49.6µs，与 NOF-153 的 44/44 同量级。
- **N>1**：`read_us` 是**每 key**，`target_us` 是**每 IO**；直接相减会把另外 N−1 个 IO 的 target 时间也算进去，**不是纯网络**。
  - 表中保留这一行（按用户口径），同时给 `res = read − N×target`；**负 res = 重叠**，不是负开销。
- 若要把“网络+框架”单独量化，需要客户端 per-IO 时间戳（本单未采集）。

### 5.4 E1 的收益为什么在 4M–256K 稳定 ~50µs、128K 掉到 17µs

- 4M–256K：E1 的 target 单 IO 差从 55.2 降到 22.7µs，但端到端差仍 46.8–57.2µs；**表现上 E1 的收益不是按“单 IO 差 ×1”传递**。可能是多个 IO 的关键路径重复享受 E1 的 push 优势，但本单没有 per-IO 时间戳，**不能确认机制**。
- 128K：E1 的 target 单 IO 反而从 17.7 回升到 26.9µs（push 13.5→21.4、W9 3.6→5.0），E0 仍降到 37.5；两侧差距缩到 10.6µs，端到端差也缩到 17.4µs。
- **128K·E1 单 IO 回升的原因未验证**；可能是 32 IO/key 下的 target 队列/JFC 压力，但本单没有 per-IO 时间戳，不能归因。

### 5.4.1 128K 的 query 差 15.5µs：不是 E1 效应

128K（N=32）的分项里，`query` E0=72.5µs、E1=88.0µs，差 15.5µs。判断如下：

- **机制上不成立**：`get_into_breakdown.query_us` 是 **Master 元数据查询耗时**（Master RPC），而 `SPDK_URMA_EID_INDEX` 只作用于 **NoF 数据面**（SPDK URMA transport），两者不在同一条路径。E1 不应改变 query。
- **数据上是离群，不是系统性偏移**：12 个臂的 query——E0：90、88、103.5、89、91、**72.5**；E1：91、96、91、96、93.5、**88**。E0 的 72.5 是全组最低；E1 的 88 仍在正常范围（88–96）。E0−E1 的 query 差逐档为 −1、−8、+12.5、−7、−2.5、−15.5，**方向不一致**（1M 反而是 E1 低 12.5µs）⇒ 没有“E1 让 query 变慢”的一致证据。
- **统计上很容易被单遍拉动**：每尺寸只有 2 遍（4M 3 遍），表中是 2 遍中位；一遍 query 偏高/偏低就能造成 10–15µs 的差。回执只给中位，**没有 per-pass query，无法确认是单遍异常还是两遍都低**；要定因需回读 `nof155_read_*.log` 的逐遍 query。
- **对 128K 结论的影响**：raw ΔP50 17.4µs 中约 15.5µs 来自 query 差；把 query 归一到同一水平，ΔP50 约 **33µs**。而 `read_us` 差 36.5µs 与 query 无关，仍说明 128K 下 E1 的数据面优势比 4M–256K 小，但**没有 raw 17.4 那么夸张**。
- **判决**：15.5µs 的 query 差**不合理作为 E0/E1 的因果差异**，合理作为**客户端/控制面漂移**；128K 的 raw ΔP50 不应作为硬结论，应同时给“归一后约 33µs”。target 侧 E1 单 IO 从 17.7 回升到 26.9µs 是另一件事，仍然成立但原因未验证。

### 5.5 push JFC 占比

- 4M/2M：93–98%；1M：89–96%；512K：83–94%；256K：76–89%；128K：80–84%。
- 回执里“push JFC 占 target 93–98%”只对 4M/2M 成立；拆细后 W9 固定开销上升（0.8→5.3µs），push 占比降到 76–84%。**E0/E1 的差仍几乎全在 push，但 push 已不是 target 成本的绝大部分**。

### 5.6 与正式口径的关系（重要）

- 正式口径：vsegment 每个 4MiB key = 2 个 2MiB child；plain = 1 个 4MiB 任务；两者默认 chunk=128KiB ⇒ **每 key 32 个 128KiB IO**（vsegment 2×16，plain 1×32）。
- 本单 128K 行就是最接近正式口径的“32 IO/key”形态：E0 P50 **258.5µs**、E1 **241.1µs**（400 keys、null bdev、diag-on）。
- 正式 NOF-127（60k、真实 target/SSD、diag 关）E0 P50：plain **248.5**、vsegment **257.0µs**，量级一致。
- 反过来，本单 4M 单 IO E1 只要 **181.2µs**。**这说明正式口径处在“多 IO、端到端偏差”的一端**（128K E0 258.5 > 4M 231.7；256K E0 289.1 更高）；如果数据路径允许放大 chunk，T1 时延可能有明显空间。但本单只证明了 **plain NoF** 的 chunk env 生效；vsegment child 是否同样生效、真实 SSD 下是否仍受益，**尚未验证**。

## 八、裁定与下一步建议

### 已可定案

1. **拆细不是 T1 时延优化**：4M→128K，target 单 IO 降 58%/19%，但每 key 端到端不降反升（E0 +27µs、E1 +60µs）。继续往 2M/1M/512K/256K/128K 更小拆，没有端到端价值。
2. **E0/E1 的单包差仍在 push JFC**：逐档 Δ 与 push JFC 差重合；但拆细后 push 占比从 93–98% 降到 76–84%，W9 固定开销上升。
3. **`read_us−target_us` 只在 N=1 时可解释为网络+框架**；N>1 必须同时给 `N` 和 `read−N×target`，负 res 是重叠，不是负开销。

### 待裁定（建议优先级）

1. **优先：反过来验证“放大 chunk”**（与 NOF-155 相反方向）。正式口径是 128KiB/32 IO，而 4M 单 IO 在 E1 下 181µs、128K 241µs。建议在真实 vsegment 路径先做 400-key 探针：`MC_NOF_SUBMIT_CHUNK_BYTES=2MiB`（每个 2MiB child 1 个 IO）vs 128KiB，E1/E0；若 vsegment 不认这个 env（NOF-015 旧结论），先停手确认代码路径，不硬推。plain 4M chunk 作为同窗口对照。
2. **target JFC 旋钮（`num_jetty_per_ep`/`jfc_depth`）暂不动**：需要重启 target，且只影响 E1 的 push 等待；在正式 128K 口径下 E1 端到端 raw 优势 17.4µs、同 query 归一后约 33µs，仍不算高，ROI 低。
3. **128K·E1 单 IO 回升不单独立项**：它已在正式口径附近，但本单 400 keys、客户端漂移 19%，不足以支撑机制结论；且 128K 的 raw ΔP50 17.4µs 含 15.5µs query 差（同 query 归一后约 33µs），更不宜据此下结论。若做第 1 项，一并复测 128K E1 即可。
4. **客户端漂移**：后续任何正式 A/B 继续保持“同窗口 + ABBA + ≥3 遍 + 完整 diag 行”；不要用单遍 400-key 的 P50 直接下结论。
