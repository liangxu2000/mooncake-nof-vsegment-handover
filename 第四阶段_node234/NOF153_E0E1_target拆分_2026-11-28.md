# NOF-153：E0 / E1 target 侧拆分（null bdev，4MiB 单包）

日期：2026-11-28

## 一句话结论

**E0 / E1 的 55µs 差额 100% 在 target 侧 `push JFC wait (C2H)`：E0 86.9µs vs E1 31.7µs；客户端 query 两侧均 109µs、`wait−drain` 残差均 22–23µs，客户端代码路径无差。** NOF-152 报的“target 33µs”是 **E1 单侧值**，同窗口 E0 一直 ~89µs；“18% 差额在客户端”的结论作废。

```
4MiB 单包（null bdev，无 SSD）
├─ 客户端 E0 / E1：query 109 / 109，wait 121 / 66，read 133 / 77
└─ target E0 / E1：TOTAL 88.6 / 33.4
      └─ push JFC wait 86.9 / 31.7   ← 55.2µs 差，100% 在这里
         W9 0.91 / 0.78（null 空介质，无意义）
```

## 2. 4MiB 单包验证

- target 每遍 n≈530（528 + 噪声），**没有 32×528 切分**。
- 客户端 `sub_ios=1 / blocks=8192`（4MiB / 512B）。
- target capsule splits **n=0**。
- 写 400 keys：`write_ops=400`、`write_bytes=1,677,721,600=400×4MiB`。

## 6. 判读

- **E1 的 18% 差额 100% 在 target 侧 URMA completion push**；不是 Mooncake 客户端、不是 SSD、不是 W9。
- 机制未验证：EID0/EID1 的 URMA 设备/物理口/jetty/JFC 映射、`num_jetty_per_ep=1`、`jfc_depth=4096` 等需要 URMA 层取证。
- 若确认是 UB 侧 EID/口差异，**“E1 更快”不是 Mooncake 能优化的**；E1 是部署/URMA 侧旋钮。
- 本案是 Mooncake NoF 端到端，不是 raw UB 带宽；单包有效带宽（diag-off）E0 17.8 / E1 21.8 GiB/s；高并发才是 46.8 / 69.4 GiB/s。

## 7. 偏差/边界

- target 统计块无时间戳/EID，按 final dump 对齐属推断；已用 NOF-152 同窗口交叉验证。
- 400 keys 样本小；P99 波动；diag-on 膨胀 12–14%；`qos_fifo_wait_us` 为 nan（plain 无 QoS 字段）。
- node4 有他人 ql client（PID 2928050，00:13 起），未清理，影响未验证。
- 未写 SSD；vseg master/etcd/target 4457 未动；Null153/sub-ss/master 测试后已清理。
